# 🤝 Contributing to APIShield

Thanks for wanting to improve APIShield! This guide keeps the repo consistent,
reviewable, and recruiter-grade — please read it before opening a PR.

## Code of Conduct

By participating you agree to uphold the [Code of Conduct](CODE_OF_CONDUCT.md).
Be respectful; assume good intent; critique code, not people.

## What needs help

- **Bugs** — check [Troubleshooting](docs/TROUBLESHOOTING.md) and open issues
  first.
- **Tests** — `gateway/` and `mcp-server/` use Node's built-in test runner;
  every fix should carry or update a test.
- **Documentation** — every README/doc is a living artifact; keep it in sync
  with code.
- **Features** — rate-limit strategies, new MCP tools, dashboard panels, n8n
  workflows, deployment hardening.

## Setting up

```bash
npm install
npm --prefix gateway install
npm --prefix mcp-server install
npm --prefix frontend install
```

Redis is required for the gateway and MCP Server. The simplest way:

```bash
docker run --name apishield-redis -p 6379:6379 -d redis:7-alpine
```

Run everything from the repo root with `npm run dev:all` (gateway + both agent
daemons + MCP Server + frontend), or target services individually — see
[Deployment — Local development](docs/DEPLOYMENT.md#1-local-development).

## Branching & commits

- Work on a feature branch: `git checkout -b feat/your-feature`.
- Keep commits focused and messages imperative ("Add …", "Fix …", "Document …").
- Reference the issue you close, e.g. `Closes #42`.
- The default branch is `main`; PRs target `main`.

## Code style

- **JavaScript/JSX**: match the existing style in the file. The frontend is
  linted by ESLint (`npm --prefix frontend run lint`).
- **Comments**: explain *why*, not *what*. Density should match surrounding code.
- **Terminology**: "APIShield Gateway", "MCP Server", "Developer Console",
  "Security Agent", "Multi-Agent Orchestrator", "Redis", "Docker Compose",
  "Kubernetes", "OpenAPI". No renaming in a drive-by PR.
- **No dead code**: remove unused assets/imports; don't leave commented-out
  blocks unless they carry a real caveat.

## Testing

Everything must pass before a PR merges (CI enforces this):

```bash
npm test                                  # gateway + MCP Server unit tests
npm --prefix frontend run lint
npm --prefix frontend run build
```

- **New behavior** ⇒ new test. Tests mock Redis, so no server is needed.
- **Docs with Mermaid diagrams** ⇒ validate the diagrams before pushing
  (`npx --yes @mermaid-js/mermaid-cli -i diagram.mmd` or the mermaid live
  editor).
- **Docs that link to files** ⇒ the target must exist; relative links are
  preferred over absolute.

## Documentation rules

1. Every new folder of substance gets a `README.md` (see the existing ones for
   the expected sections).
2. Update the [root README](README.md) when the architecture, endpoints, or
   repo layout change.
3. Keep the API surface documented in [docs/API_REFERENCE.md](docs/API_REFERENCE.md).
4. Diagrams: prefer Mermaid; verify they render.

## Committing generated files

- `k8s/secrets.yaml` is generated by `k8s/generate-secrets.sh` and is
  gitignored — never commit real credentials.
- Lockfiles (`package-lock.json`) are committed; update them with the package
  manager, not by hand.

## Reviewing a PR

- Run the test suite and the app locally.
- Check for dead links, stale docs, and unrendered diagrams.
- Leave specific, actionable feedback. Two approvals is the norm.

## Open a PR

1. Update the docs that your change touches (READMEs, docs/).
2. Push your branch and open a PR against `main`.
3. The CI pipeline runs unit tests and the frontend build automatically.
4. Request a review and address feedback; keep the conversation thread
   collaborative.

## First-time contributors

- Don't have anything big in mind? Look for issues labelled `good first issue`.
- Small documentation typo? Fix it directly — no issue needed.
